# Errors and observability

[Architecture](architecture.md) · [中文](../zh/observability.md)

Turnyard separates stable machine-readable error codes from human messages. Codes live in `internal/fault`. `fault.New/Wrap` capture the error location; `Wrap` retains the cause for `errors.Is/As`. `fault.At` names a subsystem boundary, and `fault.Ensure` gives an otherwise untyped error an `INTERNAL_ERROR` code and a location at a request or background-task boundary. `observe.LogFailure` consistently records the code, origin, operation chain, innermost cause type, and applicable process exit status, system error number, or cancellation/deadline marker without copying the cause text or agent output into operational logs. Invocation and publication failures can also record a stack captured with a fixed message. SQLite events retain task outcomes and codes, not complete Go error chains.

RPC responses contain a `request_id`; primary task correlation values flow through `context.Context` into the engine, agent, and sandbox. Independently managed child tasks have their own task IDs. JSON logs correlate request, session, task, and invocation IDs. Failed container removal retains the process exit cause and records the affected invocation and phase. When connector delivery becomes `unverified`, capturable operation failures are also logged locally. The original error chain remains in the current process; after RPC serialization, use the request and task IDs to find its log record. Agent output, task text, and credentials stay out of operational logs.

The log's `sites` field lists source locations along the error chain, so a recovery error can be traced from its entry point to the sandbox or store failure. `operations` lists the corresponding phases. Image identity checks retain the OCI command failure: `IMAGE_MISSING` is used only when the command explicitly reports a missing image; CLI or daemon failures use `IMAGE_INSPECT_FAILED`.

New error paths follow four rules: use `fault.New` for a domain decision, `fault.Wrap` to retain a system or third-party cause, `fault.At` to name a subsystem boundary, and `fault.Ensure` with `observe.LogFailure` at request and background-task exits. Ignore a return value only for cleanup that cannot affect the outcome. If cleanup affects task state, confirm that the external resource is gone; otherwise retain `unknown` or `unverified`.

`context` controls cancellation and deadlines for synchronous requests, Git clones, container processes, and checks. An asynchronous task retains correlation IDs after the request returns and continues under its own execution limit. Container cleanup uses an independent bounded context so cancellation does not prevent cleanup confirmation. Some low-level errors from external inputs are deliberately withheld: for example, a failed signed-URL download does not put the complete URL in the CLI error, while the log retains a message-free error type and origin.

These are local traceable records; **OpenTelemetry and Sentry exporters are not integrated yet**. Adding the error library does not automatically send error reports. An OpenTelemetry span and OTLP exporter can later be added at the `observe` boundary; recording an error should also mark the span as failed. Sentry's Go SDK is an option for centralized alerts after defining redaction, sampling, and deployment configuration. References: [OpenTelemetry Go status and exporters](https://opentelemetry.io/docs/languages/go/), [Go error recording and context](https://opentelemetry.io/docs/languages/go/instrumentation/), [Sentry Go SDK](https://github.com/getsentry/sentry-go), and [CockroachDB error chains and safe details](https://github.com/cockroachdb/errors).
